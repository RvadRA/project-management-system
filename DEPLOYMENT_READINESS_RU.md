# Готовность PMS к запуску и развёртыванию

Отчёт по текущему состоянию репозитория. Он описывает то, что реально есть в проекте, и отделяет проверенный локальный запуск от будущего production-развёртывания. Это аудит конфигурации и тестов, а не нагрузочное или внешний security-тестирование.

## Краткий вывод

Локально проект можно запускать с PostgreSQL и отдельно использовать Docker для PostgreSQL. **Текущая конфигурация Docker не разворачивает всё приложение.** В репозитории пока нет production Dockerfile/Compose, production web-сервера и проверенного рецепта переноса данных. Не публикуйте приложение в интернете, пока не выполнены блокирующие пункты ниже.

| Приоритет | Наблюдение | Что требуется |
|---|---|---|

## Что проверено

- Django `check` проходит; `check --deploy` выдаёт предупреждение `security.W021` (не включён HSTS preload). Это не заменяет проверку реального HTTPS/reverse proxy.
- Windows PostgreSQL `pms_db` содержит пользовательские данные и проходит `migrate --check`. Её нельзя заменять пустой Docker-БД.
- `pms_synthv2_test` — отдельная синтетическая база; у неё есть ожидающая миграция `token_blacklist.0013_alter_blacklistedtoken_options_and_more`. Не применяйте миграцию к ней без резервной копии и необходимости.
- Docker Compose поднимает только PostgreSQL 15, проброшенный на `127.0.0.1:5433`, с постоянным Docker volume. Это отдельный экземпляр БД, не Windows PostgreSQL на `localhost:5432`.
- Frontend tests/build: 62 теста проходят; TypeScript/Vite production build успешен. Lint ранее завершился с 200 errors и 4 warnings; lint целевых файлов изменённого дашборда проходит без предупреждений.
- После исправлений повторный полный Django test run: 322 теста за 210 секунд, `OK`, exit code 0. Прогон использовал тестовую БД, не пользовательскую `pms_db`. Ранее падали проверки AI task drafting/status и matching availability; добавлена обработка отсутствующего описания в ответе модели, изолирован тест статуса STT, а ожидания доступности приведены к явно заданной политике нейтрального значения при неизвестной загрузке.
- Это не нагрузочный тест. Оценки ресурсов ниже — начальная рекомендация, не гарантия достаточной производительности.

## Что исправить до production

### Обязательные технические работы

1. **Выбрать production-схему и сделать её воспроизводимой.** Предпочтительный целевой вариант: Nginx/HTTPS → Django под production WSGI-сервером; PostgreSQL; Redis, Celery worker и Celery Beat, если нужны фоновые задачи. У каждого stateful-компонента должны быть явные health checks, персистентные данные и процедуры резервного копирования.
2. **Добавить production packaging.** Сейчас нет Dockerfile приложения, production Compose, Nginx-конфигурации и CI workflow. Compose с одной БД не является production-деплоем. Не используйте dev-сервер Django или Vite на публичном сервере.
3. **Сверить конфигурацию.** Django читает `DJANGO_DEBUG`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `CELERY_BROKER_URL` и другие переменные из [`config/settings.py`](./config/settings.py). Старый [`DEPLOYMENT.md`](./DEPLOYMENT.md) описывает, среди прочего, `DEBUG`, `DATABASE_URL`, `ALLOWED_HOSTS` и `REDIS_URL`, которые сами по себе не настраивают эти параметры текущего проекта.
4. **Закрыть пользовательские файлы.** Не публикуйте весь `/media/` через Nginx: документы задач/проектов/базы знаний должны оставаться за авторизацией. Реализуйте авторизованную выдачу, например через проверку API с `X-Accel-Redirect`, и проверьте доступ под разными ролями.
5. **Добавить WSGI-сервер в зависимости.** В [`requirements.txt`](./requirements.txt) сейчас нет Gunicorn. Выберите совместимый сервер, зафиксируйте версию и проверьте запуск, graceful shutdown, таймауты и логи на целевой ОС.
6. **Настроить production email.** Сейчас используется console backend; добавьте явные настройки SMTP/провайдера из переменных окружения и тест доставки, не храня секреты в Git.
7. **Исправить тесты и качество сборки.** Разобрать backend failures, устранить или документировать frontend lint-ошибки; настроить CI: backend tests, frontend tests, build/lint, migration check и проверку конфигурации.
8. **Подготовить эксплуатацию.** Добавить структурированные логи, мониторинг/оповещения, endpoint готовности, ротацию логов, процедуру обновления и проверенный rollback.

### Данные и секреты

- Не переносите в production локальную базу простым подключением к Docker-контейнеру. Сначала сделайте зашифрованную резервную копию нужной БД и файлов, проверьте восстановление в изолированной среде и только затем выполняйте управляемый импорт.
- Docker-БД на порту 5433 и локальная Windows-БД на 5432 — разные экземпляры. Сравните адрес, порт и имя базы перед любой миграцией или импортом.
- Не запускайте `seed_data` на production: команда создаёт demo-учётные записи. Создайте отдельного администратора через `createsuperuser`; немедленно задайте уникальные пароли.
- Поскольку секреты и известные пароли могли попасть в историю репозитория, ротация только в текущем `.env` недостаточна: замените production Django secret, пароли БД/Redis/SMTP и ключи интеграций; отзовите JWT refresh tokens. Удаление строк из последнего коммита не удаляет их из истории Git.
- Храните `.env`/секреты вне репозитория с ограниченными правами доступа. Не вставляйте секреты в командную строку, логи, тикеты и этот отчёт.
- Для Compose осторожно задавайте секреты с символом `$`: Compose может интерполировать его в dotenv/config. Проверьте конфигурацию без вывода секретов и применяйте утверждённый способ хранения secret.

## Требования к серверу

Платформа-пример для production: Linux x86_64 с поддерживаемыми версиями Python/Node/PostgreSQL, HTTPS и постоянным диском. Версии ниже — стартовые ориентиры из текущего окружения проекта (Python 3.14, Node 24, Django 6.0); зафиксируйте и протестируйте совместимый набор до развёртывания.

| Профиль | Начальная оценка | Состав |
|---|---|---|
| Разработка | 4 CPU, 8 GB RAM, 30+ GB свободного SSD | Приложение, тестовая БД; Ollama лучше запускать отдельно, если памяти недостаточно. |
| Небольшой production без локального LLM | 2–4 vCPU, 8 GB RAM, 40+ GB SSD | Django, PostgreSQL и Redis/Celery с небольшой нагрузкой. Лучше размещать БД отдельно или обеспечить отдельные резервные копии/диск. |
| Production с локальным Ollama | от 4 vCPU, 16 GB RAM, 60+ GB SSD; больше при одновременных запросах | Модель и embeddings занимают диск и RAM; реальное потребление зависит от модели, контекста и параллельности. 8 GB может оказаться тесно. |

Нужны домен, TLS-сертификат, firewall, SSH-доступ администратора, стабильный диск для PostgreSQL/media/model cache, резервное хранилище вне сервера и исходящий доступ только к необходимым сервисам. Для роста пользователей/данных эти цифры надо заменить результатами нагрузочного теста и планом восстановления.

## Порядок развёртывания

**Важно:** приведённые ниже шаги — целевой порядок, а не готовая команда `docker compose up` для текущего репозитория. Полный production Compose и конфигурация веб-сервера ещё не созданы.

### Этап 1. Подготовить проект

1. Выберите способ запуска: контейнерный production stack либо отдельные systemd-службы. Определите, где хранятся PostgreSQL, media и, если нужны, Redis/Ollama.
2. Добавьте и проверьте отсутствующие артефакты: production Dockerfile/Compose (если выбран Docker), web-server config, WSGI dependency, worker/beat services, секреты, health checks, backup/restore scripts и CI.
3. Уточните переменные окружения по фактическим именам в [`config/settings.py`](./config/settings.py). Задайте `DJANGO_DEBUG=False`, уникальный `DJANGO_SECRET_KEY`, точные `DJANGO_ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS`, production `DB_*`, `DJANGO_USE_HTTPS=True` и `CELERY_BROKER_URL`, если запускаются фоновые задачи.
4. Подготовьте релиз из Git: зафиксированные зависимости, frontend build, миграции, сборка static assets. Убедитесь, что dev-серверы и demo seed не используются.

### Этап 2. Подготовить сервер и данные

1. Обновите ОС, создайте отдельную учётную запись развёртывания без постоянного root-доступа, настройте SSH-ключи и firewall. Откройте только необходимые порты (обычно SSH и 80/443); не публикуйте PostgreSQL/Redis наружу.
2. Установите выбранный runtime и зависимости. Если выбран Docker, установите Docker Engine/Compose на Linux-сервер; Docker Desktop/WSL — это инструмент разработки на Windows, а не production-сервер.
3. Создайте пустую production БД и отдельного ограниченного пользователя БД. Настройте TLS для публичного сайта и безопасное хранение secrets.
4. Сделайте backup исходных БД и необходимых файлов; проверьте восстановление копии в тестовую среду. Решите, какие данные из `pms_db` переносить. Не импортируйте `pms_synthv2_test` как рабочие данные.

### Этап 3. Развернуть релиз

1. Получите проверенный release/commit на сервере и установите зависимости из lock/pinned manifests.
2. Соберите frontend для production и настройте Nginx на static assets и проксирование API к production WSGI-серверу.
3. Настройте доступ приложения к PostgreSQL, Redis/Celery и Ollama (если используются). Внутри контейнера `localhost` указывает на этот контейнер, а не на Windows-хост или соседний сервис: используйте service DNS/адрес выбранной схемы.
4. Запустите `python manage.py check --deploy` в production-окружении и устраните предупреждения, включая настройку HSTS после проверки HTTPS/proxy. Проверьте `python manage.py migrate --check`, затем сделайте backup и примените миграции отдельным контролируемым шагом.
5. Выполните `python manage.py collectstatic --noinput`, запустите WSGI/worker/beat только для нужных функций и настройте автоперезапуск служб.
6. Перед переключением DNS проверьте HTTPS, вход/выход, роли и запрет доступа к чужим проектам/файлам, загрузки, email, фоновые задачи, логи и восстановление backup. Проведите smoke test без demo credentials.
7. Переключите DNS/трафик, наблюдайте за ошибками, latency, диском, памятью, очередями и БД. При проблеме верните предыдущий release; миграцию схемы откатывайте только по заранее проверенному плану.

## Обновление и резервное копирование

- Каждый релиз: backup БД и важных пользовательских файлов → проверить release/тесты → применить совместимые миграции → переключить приложение → smoke test → сохранить предыдущую версию для rollback.
- Backup должен храниться отдельно от сервера, быть зашифрован и регулярно проверяться восстановлением. Согласуйте RPO/RTO (допустимую потерю данных и время восстановления) с владельцем системы.
- Не удаляйте старый Docker volume и не выполняйте `docker compose down -v`, пока не подтверждены backup и нужность данных.
- Изменения моделей БД должны быть обратно совместимы на время перехода старых и новых процессов. Для сложных изменений используйте расширение схемы и отдельное удаление устаревших полей в следующем релизе.
- После восстановления проверьте `manage.py check`, состояние миграций, вход, доступы и целостность файлов.

## Команды для локальной проверки

Запускайте backend tests только с настроенной тестовой БД и проверьте конфигурацию подключения перед тестами. Для локального Docker PostgreSQL используйте опубликованный Compose-порт `5433`; для основной Windows `pms_db` — только её действующий адрес и порт. Не запускайте миграции или тесты, пока не убедились, к какому экземпляру подключается Django.

```powershell
python manage.py check
python manage.py check --deploy
python manage.py migrate --check
python manage.py test
```

python manage.py check
